01 / Machine learning & language models

PythonGPT

Starting from the same base weights as Qwen’s own Instruct model, I built a post-training pipeline that nearly matches it on HumanEval+ and beats it on MBPP+.

Python · PyTorch · Qwen2.5-Coder · DeepSeek API · Docker · EvalPlus · GRPO · H100

Same starting point, same benchmarks.

Qwen released two versions of its 0.5B coding model: a raw base checkpoint and an Instruct model, which Qwen’s team post-trained from that base. The base, Qwen2.5-Coder-0.5B, has 494M parameters. It can complete code, but it can’t follow instructions. PythonGPT starts from the same base and turns it into a Python coding assistant that takes a task and writes a correct, self-contained standard-library function.

The project had two aims. One was to learn post-training by building each step myself: data curation, supervised fine-tuning (SFT), benchmarking and reinforcement learning. The other was to match Qwen’s official Instruct model under the same measurements.

After three SFT stages and a final round of execution-reward RL (GRPO), the model passes 54.3% of HumanEval+ against the Instruct model’s 54.9%, and 53.4% of MBPP+ against 43.9%, with both models graded by the same harness.

S1: the first pass

The first checkpoint trained on the full OpenCoder educational_instruct subset, about 118K rows, in Qwen’s chat format, with loss computed only on the answer. It ran on my home PC (an RX 9070 XT under ROCm in WSL2), which first meant tracking down missing ROCm runtime libraries. Late in the run the loss turned into NaN; I recovered by resuming from a checkpoint saved before the failure.

The same stage produced the evaluation tools every later row depends on: an inference script, HumanEval+ answer generation and a sandboxed Docker grader. S1 scored 28.0% on HumanEval+, up from 9.1%.

Building the training set

More rows of the same kind were not likely to help, so for S2 I rebuilt the data around one rule: a row counts only if its code runs and its tests pass. Each source gets its own adapter. The adapters keep code only, reject third-party imports and unsafe calls, re-run each row’s tests in Docker, and remove exact and near repeats. They also compare every row against all 542 HumanEval+ and MBPP+ tasks by function name and wording, so benchmark tasks stay out of training.

A study of why OpenCodeInstruct rows failed the filter showed that most rejected rows had broken generated tests, not broken code.

The checks also caught a leak in the data itself: 20% of KodCode prompts ended with their own pytest tests, so the model could see the answer’s test cases inside the question. I found and fixed the bug before it reached training.

Distilling a teacher

Asking a model to “be diverse” produces repeats, so the program decides the mix. It assigns each question a skill from a list of about 235, a form and a difficulty, and DeepSeek writes the questions. A second stage writes a solution plus six to ten test asserts for each. A third runs every solution against its tests in a locked-down Docker container. After a review I tightened the checks: every test must call the function, the signature must match the question, stubs must include docstring examples that the solution passes, and a retry must also pass the test that failed the earlier attempt.

Training

A hand-written training loop

For S2 I replaced the library trainer (TRL’s SFTTrainer) with train_torch.py, a training loop written by hand in plain PyTorch. Batches are capped by padded token count rather than row count, so long and short rows don’t waste memory on padding. Loss is averaged per token over each 64-row update however it is split into chunks, so splitting never changes the gradient. The schedule is warmup followed by cosine decay, with gradient clipping, and checkpoints resume exactly. Before renting a GPU, I checked the loop against TRL on one batch and tested resume on my Mac.

  • NaN gradients. The first S2 runs died with non-finite gradients. The cause was PyTorch’s cuDNN attention kernel on padded bf16 batches; turning that kernel off fixed it.
  • Memorization. In S2’s third epoch, validation loss jumped: the model had started memorizing. S3 continued from the epoch-2 checkpoint instead.
  • Loss picked the wrong checkpoint. In S3, the checkpoint with the lowest validation loss was worse on every benchmark than the final one. From then on, checkpoints were chosen by running tests.

S3 shrank the gap to Qwen on HumanEval+ from 34 tasks to 7.

Reinforcement learning on executed tests

Before RL, I read S3’s failures task by task. They were mostly logic errors that contradict the examples in the prompt, not formatting problems. S3 solves 72% of HumanEval+ tasks in at least one of 10 samples (pass@10), and 39% of unseen tasks gave mixed pass and fail results across samples. Mixed results are what RL needs to learn from.

The GRPO trainer samples eight answers to each task, runs each one against hidden tests, and gives a reward of 1 only if every test passes. Advantages are normalized within each task’s group of eight, so passing answers become more likely relative to failing ones on the same task.

The best run added 3.7 points on HumanEval+ and 2.3 on MBPP+ over S3. Those gains are small and close to run-to-run noise.

What I learned

  • Data mattered most. Distinct, test-verified data that matches the benchmark’s prompt shape (a signature plus a docstring) gave far bigger jumps than tuning the recipe. The S2 → S3 data change alone was worth 16.5 points on HumanEval+.
  • Choose models by running tests. Validation loss and the small held-out pass rate both picked the wrong checkpoint or learning rate.
  • More epochs memorize. The third pass over the data hurt; adding more distinct rows helped.
  • Make runs reproducible. Every run has a log, revisions are pinned, and comparisons use the same protocol, all recorded in the training log.

Limits

  • The model answers only in code, never in prose, because every training answer was code-only. Chat-style SFT rows would fix this.
  • GRPO gains are close to noise. Bigger or better-targeted RL runs are the obvious next experiment.
  • Small models, mine and Qwen’s, are near zero on unseen competition problems (LiveCodeBench). These benchmarks measure short standard-library functions.
  • The benchmark screen matches function names and wording; it can’t catch the same problem in different words, and the base model’s pretraining data can’t be audited.
  • In distillation, the teacher writes both the solution and its tests, so a shared misunderstanding can pass.
